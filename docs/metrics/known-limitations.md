# Known Limitations

This document collects limitations that apply broadly across the LucidUI deterministic metric engine, beyond the per-metric limitations already listed in [metric-catalog.md](metric-catalog.md). It exists so that every consumer of LucidUI's output — the LLM interpretation stage, the frontend, and researchers — has a single place to understand what the numbers do and do not mean.

## Measurement Limitations

- **Contrast Sampling V4 — dual estimate (`corrected-v3`)**: contrast is computed by Otsu-separating each OCR text region into ink/paper pixel clusters, then estimating foreground color two ways from the ink cluster — a **core** estimate (per-channel median of only the darkest/lightest 15%) and a **conservative** estimate (per-channel median of the entire cluster) — against a shared border-connected background estimate. A region is a confirmed pass/fail only when both estimates agree; when they don't, it is reported `uncertain` / `aaResult: "borderline"` with both ratios and the resulting range, never forced to a single value. This exists because a cross-check against three independent whole-region methods (Otsu-cluster mean, percentile-decile, k-means) found the prior single-estimate `corrected-v2` (V3) measurably higher than all three on small anti-aliased paragraph text — internal consistency across repeated runs of one method is not evidence that method is accurate relative to a genuinely different one, and the gap was large enough to flip the WCAG AA classification. Which estimate (if either) matches the *original design/CSS color* cannot be determined from pixel data alone without that external source — `borderline` is the honest answer when the two disagree, not a claim that either is wrong. Otsu still assumes each text region is meaningfully bimodal; text over a busy photo or gradient, or a region whose ink cluster/core sample is too small (<10px / <5px), is reported `uncertain` (`regionsUncertain`) rather than fabricated, and a flat/near-zero-variance region is skipped (`regionsSkipped`). The 15% core percentile and the 10px/5px minimum-sample thresholds are fixed constants, not derived from the analyzed image.
- **OCR word-level element inflation**: OCR frequently detects individual words as separate boxes, inflating detected element and text density counts relative to semantic UI elements. `corrected-v1` excludes OCR-sourced boxes from the small-target tally and from Fitts's Law specifically (they were never tap-target candidates), but `detectedElementCount`/`wordsDetected`/`textDensityRatio` themselves are still one-box-per-word.
- **No resolution normalization**: metrics like edge density and detected element count are sensitive to the screenshot's pixel resolution; two screenshots of the same UI at different resolutions/DPI can produce different raw values.
- **44px small-target threshold is raw-pixel, not device-independent**: the 44px comparison (contour-sourced elements only, as of `corrected-v1`) is against raw screenshot pixels, never a CSS/device-independent-pixel value — a real ~44pt control captured at 3× device scale is ~132 raw px and will simply never be flagged, while the same control captured at 1× will be compared directly. No device-pixel-ratio is read or inferred from the image.
- **Repeating-grid exclusion is a heuristic (`corrected-v1`)**: `filteredElementCount`/`repeatingGridExcludedCount` (feeding Hick's Law) detect a dense horizontal band of ≥8 near-uniform-size contour elements (e.g. an on-screen keyboard) via fixed height/width-uniformity thresholds. This is tuned against a small validation set and can miss non-keyboard repeating grids or, rarely, exclude a genuinely dense row of real app content. This caveat is also disclosed directly in the `elements.source` JSON field (`corrected-v2`), not only here.
- **Hick's Law `b` constant is unsourced (`corrected-v2`)**: `hicksLawEstimateMs`'s `b=150ms` (exposed as `hicksLawBConstantMs`) is an assumed, illustrative constant, not a value derived from Hick (1952) or any other cited empirical source — see [scientific-references.md](scientific-references.md#hicks-law). Treat `hicksLawEstimateMs` as an uncalibrated relative estimate, not a predicted decision time in real milliseconds.
- **Complete-linkage clustering threshold (`corrected-v1`)**: group count uses the same fixed distance constant (8% of image diagonal) the prior single-linkage version used, just with a linkage rule that resists chaining a long dense region into one cluster. The constant itself is not derived from the analyzed UI and can still over- or under-split relative to human-perceived sections.
- **Fixed Canny thresholds**: edge detection uses fixed threshold parameters rather than per-image adaptive thresholds, which can under- or over-detect edges depending on image characteristics.
- **Light-background assumption in whitespace detection (`corrected-v1`)**: a block now counts as whitespace-like only if it is both low-variance *and* light (mean > 200/255) — this removes the prior false-positive where a flat *saturated* color counted as whitespace, but it means the check is now explicitly light-background-oriented and will under-detect "flat, intentionally empty" regions on dark-mode or unusually-themed interfaces. This threshold, and the 8px `alignedElementRatio` edge-tolerance, were tuned against a small internal set of real screenshots, not a systematic or statistically powered validation study; also disclosed directly in the `whitespaceAlignment.source` JSON field (`corrected-v2`), not only here.
- **Hue-diversity constants (`corrected-v1`)**: the hue-diversity saturation cutoff (40) and histogram bin count (36) are fixed, not derived from the analyzed image.

## Implementation Limitations

- **Single shared OCR pass**: as of Phase 2B-1, `app.metrics.MetricEngine` runs Tesseract OCR at most once per analysis and shares the resulting word/box data across contrast, element detection, and text density. This is an intentional performance choice (see [ROADMAP.md](../../ROADMAP.md) Phase 2B-1), but it also means a single OCR miss or false detection propagates into all three of those metrics simultaneously for that analysis, rather than affecting them independently. If OCR execution is unavailable, those metrics are computed from empty OCR data.

## Scope Limitations

- **Screenshot-only limitations**: LucidUI never has access to the live DOM, CSS, or application state — only a static raster image.
- **No DOM or interaction semantics**: LucidUI cannot know which detected regions are actually clickable, focusable, or interactive; it can only report visual/geometric properties.
- **Proxy metrics**: nearly every metric in the catalog is an approximation of a cognitive-science or HCI construct (Hick's Law, Fitts's Law, Miller's grouping heuristic), not a direct behavioral measurement — see each metric's Proxy Status in [metric-catalog.md](metric-catalog.md).
- **Screenshot crop and framing effects**: partial screenshots, scrolled views, or cropped captures can materially change element counts, density, and balance metrics without the underlying UI actually changing.
- **Font rendering and anti-aliasing effects**: how text and edges render (browser, OS font rendering, anti-aliasing, screen scaling) can shift edge-density, contrast, and font-size-diversity readings independent of actual design differences.

## Cross-System Limitations

- **UIClip training-data dependence**: UIClip's output reflects patterns in its training data and is not a neutral or universal standard — see [docs/research/uiclip-integration.md](../research/uiclip-integration.md). This applies to the real/official model; as of Phase 4, `uiclip` output is produced by `MockUIClipProvider` (a fixed, illustrative placeholder), not the real model, and carries no training-data dependence of its own.
- **UIClip score has no confirmed universal normalization**: the official UIClip score is an uncalibrated dot-product similarity/logit value, not a documented 0-100 or 0-1 quality percentage — `uiclip.normalizedQualityScore` is intentionally left `null` rather than computed via an invented conversion. See [docs/research/uiclip-integration.md](../research/uiclip-integration.md).
- **LLM interpretation dependence on input metrics**: the LLM interpretation stage can only be as accurate as the deterministic metric JSON it receives; it has no independent visual verification since it never sees the raw image (see [ADR-003](../architecture/decisions/ADR-003-json-only-llm-input.md)).

## How These Limitations Should Be Used

- In documentation and frontend copy: to justify hedged, non-verdict language (see [docs/frontend/FRONTEND_GUIDE.md](../frontend/FRONTEND_GUIDE.md) language guidelines).
- In research work: as caveats that must be disclosed alongside any correlation or benchmarking result (see [docs/research/evaluation-plan.md](../research/evaluation-plan.md)).
- In future implementation work: as a checklist to revisit before claiming a metric has been "fixed" or "improved" — most limitations here are inherent to screenshot-based analysis and are not fully solvable, only reducible.
