# Metric Reliability Tiers

This document classifies every metric in the [metric catalog](metric-catalog.md) into three reliability tiers — **Sound**, **Approximately Correct**, and **Problematic** — so a consumer of LucidUI's output (the LLM interpretation stage, the frontend, or a researcher) can tell at a glance how much weight a given number deserves, without reading the full audit trail in `app.metrics.corrected`'s module docstring each time.

This is a synthesis, not a new judgment: every classification below is derived directly from findings already recorded in [metric-catalog.md](metric-catalog.md), [known-limitations.md](known-limitations.md), [scientific-references.md](scientific-references.md), and the fix-by-fix audit trail in `backend/app/metrics/corrected.py`. Nothing here overrides those documents — if this file and one of them ever disagree, the other document (or the code) is authoritative and this file is stale.

Per [CLAUDE.md](../../CLAUDE.md)'s "Flashlight, Not a Judge" principle, a tier is not a verdict on the *design* being analyzed — it is a statement about how much to trust the *measurement itself*. See [interpretation-taxonomy.md](interpretation-taxonomy.md) for the separate, orthogonal question of what conclusions the LLM interpretation layer may draw from a metric (Actionable / Diagnostic / Descriptive) — a Tier 1 "Sound" metric like Visual Balance can still be Interpretation-taxonomy "Descriptive" (no validated normative threshold exists for asymmetry), because the two documents answer different questions.

## Tier Definitions

- **Sound** — the underlying formula/statistic is a correctly implemented, either published-and-unmodified (e.g. Hasler–Süsstrunk colorfulness, WCAG contrast ratio) or audit-verified computation, with no known accuracy defect. Proxy/interpretation limitations may still apply (see each metric's Proxy Status) — "Sound" is about computational correctness, not about how closely the proxy tracks the human construct it is named after.
- **Approximately Correct** — the computation is a legitimate, deliberately-fixed method that measurably improved on a known prior defect, but it still depends on fixed constants or thresholds that were tuned against a small internal screenshot set (not a systematic or statistically powered validation study), or on an input (OCR, a proxy element list) whose own error rate is not fully corrected for. Treat the value as directionally trustworthy, not exact.
- **Problematic** — the metric has a specific, disclosed structural weakness that can materially mislead a reader who doesn't already know the caveat: an unsourced constant presented as if empirically derived, a raw-pixel comparison against a device-independent guideline, a heuristic with a documented false-positive/negative mode, or (for composite scoring) a normalization rule that contradicts the metric's own documented interpretation guidance.

A metric can appear in more than one tier if different parts of its output deserve different trust levels (e.g. Contrast's core computation vs. its fixed sampling constants).

## Tier 1 — Sound

| Metric / Field | Why it's Sound |
|---|---|
| `contrast_ratio`, `relative_luminance` (shared by all contrast versions) | Explicitly verified mathematically correct by the audit and left unmodified — see the `app.metrics.corrected` module docstring: "Two functions the audit verified as mathematically correct are reused unchanged from the legacy module." |
| Colorfulness (`colorfulnessScore`) | Hasler & Süsstrunk (2003) formula, implemented and unmodified; the audit confirmed "the formula itself is unchanged (correct as published)." Only its *name* invited a misreading (see [Hue Diversity](#tier-2--approximately-correct) below), not its math. |
| Hue Diversity (`hueDiversityIndex`) computation | Shannon entropy of a hue histogram, normalized by `log2(bin_count)` — a standard, correctly-implemented information-theoretic statistic (the saturation cutoff and bin-count constants are addressed separately in Tier 2). |
| Font-Size Diversity Proxy — MAD statistic | Median absolute deviation is the correct, more outlier-resistant replacement for the prior std-dev computation; the audit's stated goal ("a single OCR misdetection ... can otherwise dominate a std-dev-based figure") is what MAD is designed to solve. |
| Visual Balance (`asymmetryScore`) | A simple, unambiguous left/right and top/bottom mean-luminance difference — the arithmetic has no known defect; its *semantic* meaning (brightness balance, not compositional balance) is a Proxy Status caveat, not a correctness one. |
| Fitts's Law formula (`ID = log2(2D/W)`) | Correctly implements Fitts (1954)'s index-of-difficulty formula. What feeds it (which elements count as targets) is addressed under Tier 2/3 — the formula application itself is sound. |
| Contrast V4's core computation logic (Otsu split → dual foreground estimate → agree/disagree) | A cross-check against three independent whole-region methods (Otsu-cluster mean, percentile-decile, k-means) drove this design specifically so the metric never silently picks a side it can't justify — a region is reported `borderline` rather than forced to one number when the two internal estimates disagree. This is the most rigorously stress-tested metric in the engine. (Its fixed sampling constants are Tier 2 — see below.) |
| `_extract_contour_elements`'s CCOMP/hole/background/duplicate handling | Fixed a real, demonstrated false-negative (a full-bleed-background modal screen reporting **zero** elements) via `cv2.RETR_CCOMP` plus three independently-verified filtering layers (hole exclusion, background classification, containment+IoU+area-ratio deduplication), each disclosed via its own count field rather than silently applied. |

## Tier 2 — Approximately Correct

| Metric / Field | Reasonably reliable, but... |
|---|---|
| Contrast (`averageContrastRatio`, `regionsBelowAAThreshold`, `aaResult`) | The dual-estimate method is Sound (above), but the 15% core-percentile cutoff and the 10px/5px minimum-sample thresholds are fixed constants, not derived from the analyzed image, and — as [known-limitations.md](known-limitations.md) states outright — "which estimate (if either) matches the *original design/CSS color* cannot be determined from pixel data alone." Treat `borderline` regions as genuinely undetermined, not as a rounding error. |
| Detected Element Count (`detectedElementCount`, `contourBasedCount`) | The contour side is well-engineered (see Tier 1), but `detectedElementCount` still includes one-box-per-OCR-word, which the catalog itself flags as inflating the count relative to semantic UI elements. Size floor/ceiling (400px²/30% of image area) are fixed constants. |
| Estimated Group Count (`estimatedGroupCount`) | Complete-linkage clustering is a legitimate, correctly-implemented fix for the prior single-linkage chaining bug (audit-confirmed: single-linkage let one dense region collapse into 1–3 clusters). But the 8% -of-diagonal distance threshold is the *same unvalidated constant* the old buggy version used, just with a better linkage rule around it, and the method uses position only — no color or semantic similarity. |
| Text Density (`textDensityRatio`) | The area-ratio computation itself is simple and correct; it is entirely downstream of Tesseract OCR quality. `averageOcrConfidence`/`lowConfidenceWordsExcluded` now disclose that dependency per-analysis, which is why this sits in Tier 2 rather than Tier 3 — the risk is measured, not hidden. |
| Font-Size Diversity Proxy (`fontSizeDiversityProxy`) | The MAD *statistic* is Sound (Tier 1), but bounding-box height is still only a proxy for font point size (affected by line height, descenders/ascenders, OCR box-fitting) — the underlying input, not the math, is approximate. |
| Fitts's Law Index of Difficulty (`averageIndexOfDifficulty`) | The formula is Sound, and it now runs only over `interactiveTargets` (glyph-excluded, grid-excluded, keyboard-excluded) rather than a contaminated element list. It still assumes a specific nearest-neighbor movement path with no real pointer origin (a static screenshot has none) — a structural proxy gap, not a bug, and one the catalog is explicit no empirical validation has yet tested. |
| Keyboard region detection (`keyboardDetected`, `keyboardDetectionConfidence`) | A deliberately conservative six-signal design (geometric signals alone are capped below the detection threshold, so textual corroboration is always required) that correctly degrades to `degraded`/uncertain rather than a false confident call. Still tuned against a small internal set of real screenshots, per its own `source` field — may not generalize to unseen keyboard layouts, fonts, or scales. |
| Hue Diversity (`saturatedPixelRatio` / the saturation-40 and 36-bin constants) | The entropy math is Sound (Tier 1), but the saturation cutoff and bin count are fixed constants, "not derived from the analyzed image," per the catalog's own limitation note. |

## Tier 3 — Problematic (removed as of `corrected-v4`)

Every metric in this tier was removed from the engine/API entirely as of engine version `corrected-v4`, per explicit user instruction, for research-paper defensibility — not merely excluded from reporting. This table is kept as the historical audit trail explaining *why* each was removed (see also [metric-catalog.md](metric-catalog.md#removed-metrics-tier-3-corrected-v4) and [known-limitations.md](known-limitations.md#removed-metrics-tier-3-corrected-v4)); none of these fields are present in current output.

| Metric / Field | The specific issue |
|---|---|
| Hick's Law Estimate (`hicksLawEstimateMs`, `hicksLawBConstantMs`) | `b = 150ms` is explicitly documented as **"an assumed, illustrative constant, not a value derived from Hick (1952) or any other cited empirical source"** — Hick's original paper reports information-theoretic bits, not a milliseconds-per-bit constant. The catalog calls this metric a "proxy of a proxy" with **no empirical correlation to real human decision time established at all**. Treat the millisecond value as an arbitrary relative index, never as a time estimate. |
| Small Targets (`smallTargetsBelow44px`) | Compared directly against raw screenshot pixels, never CSS/device-independent pixels. Per the catalog: **"a real ~44pt control captured at 3× device scale is ~132 raw px and will simply never be flagged"** — this check is "only meaningful by coincidence unless the capture was taken at 1× scale," and no device-pixel-ratio is read or inferred from the image at all. |
| Whitespace Ratio (`whitespaceRatio`) | The brightness gate (`mean > 200/255`) is explicitly "light-background-oriented" — it will systematically under-detect intentional empty space on dark-mode or unusually-themed UIs, which is a large and increasingly common class of real screenshots. The variance/brightness thresholds were "tuned against a small internal set of real screenshots, not a systematic or statistically powered validation study." |
| Alignment (`alignmentVariance`, `alignedElementRatio`) | The 8px edge-tolerance is a fixed constant "not derived from the analyzed UI's actual grid unit." The catalog warns outright that "intentional asymmetric layouts will register as high variance without being a design flaw" — this metric cannot distinguish an inconsistent layout from a deliberately asymmetric one. |
| Edge Density / Clutter (`edgeDensity`) | Still the untouched `legacy-v1` implementation — fixed Canny thresholds (100/200), no per-image adaptivity, and explicitly "not normalized across screen sizes." This metric was out of scope for the correction audit entirely and carries none of the disclosure improvements applied elsewhere. |
| Repeating-grid exclusion (`repeatingGridExcludedCount`) | A geometric heuristic (row/column count floors, size-uniformity and gap-ratio cutoffs) "tuned against a small internal set of real screenshots" per its own `source` field — it can still miss a non-keyboard repeating grid or, rarely, wrongly exclude a genuinely dense row of real app content. |
| Raw-pixel thresholds vs. resolution (multiple metrics) | Every fixed-pixel constant in the engine (the 400px² contour floor, the 44px small-target check, the 8px alignment tolerance, the 20px whitespace block size) is defined in raw analysis pixels. The `_REFERENCE_ANALYSIS_WIDTH` upscaling fix (`corrected-v3`) only equalizes these *for images narrower than 390px* — two exports of the same design that are **both already at or above** that floor, but at different native widths, are explicitly **not** normalized against each other. This is a known, disclosed gap, not a claim of full resolution invariance. |
| **Composite Score — `normalize_group_count`** | This was the one internal **inconsistency** found while assembling this document, not just an inherited limitation: `normalize_group_count(n) = 100 - abs(n - 7) * 15` computed the composite score's `groupCount` component by penalizing deviation from exactly 7 groups. But [metric-catalog.md](metric-catalog.md#estimated-group-count) explicitly instructs: **"Must not claim that 7 (or 7 ± 2) is an ideal or universal target number of UI groups — Miller's number describes short-term memory chunk capacity in a different experimental context, not UI design guidance."** The normalization function did exactly what the metric's own documentation says never to imply. **Resolution (`corrected-v4`)**: `groupCount` (along with `clutter`/`elementSize`, the other two Tier 3 composite inputs) was dropped from the composite score entirely — see `WEIGHTS_V2`/`normalize_metrics_v2`/`weighted_score_v2` in `backend/app/metrics/corrected.py` and [scoring-and-normalization.md](scoring-and-normalization.md). The raw `estimatedGroupCount` metric itself (Tier 2, above) is unaffected and still reported — only its use as a composite-score input was removed. `legacy_metric_engine.py`'s original `normalize_group_count`/`WEIGHTS`/`normalize_metrics`/`weighted_score` remain untouched (immutable) and simply unused, per the same "add a new version, never edit the legacy file" pattern used throughout `corrected-*`. |

## How to Use This Document

- **In the LLM interpretation layer**: an observation built primarily from a Tier 2 field should still be hedged more strongly ("a potential review area, given known measurement limitations") than one built from Tier 1 data — see [ADR-003](../architecture/decisions/ADR-003-json-only-llm-input.md) and the LLM Rules in [CLAUDE.md](../../CLAUDE.md). Tier 3 fields no longer exist in the metric JSON as of `corrected-v4`, so this no longer applies to any live field.
- **In the frontend**: consider surfacing tier or confidence alongside any Tier 2 value, consistent with the non-verdict language guidance in [docs/frontend/FRONTEND_GUIDE.md](../frontend/FRONTEND_GUIDE.md).
- **In research work**: a correlation or benchmarking study (see [docs/research/evaluation-plan.md](../research/evaluation-plan.md)) should treat Tier 1 metrics as the primary signals worth validating against human ratings first, and Tier 2 as secondary/exploratory. Tier 3 metrics are no longer available to use as a baseline at all — they were removed, not merely deprioritized.
- **On the Tier 3 removal itself**: per [CLAUDE.md](../../CLAUDE.md), the deterministic engine's formulas, thresholds, weighting rules, and public API fields must not be modified or removed except by explicit instruction. The Tier 3 removal in `corrected-v4` is exactly that explicit-instruction exception, executed once, for research-paper defensibility — it is not a precedent for removing a Tier 2 or future finding without the same explicit sign-off.
